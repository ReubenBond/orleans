# Invariants and correctness

- **Invariants in both directions.** Each affected boundary states what it guarantees and requires, using types where practical, XML docs for non-obvious caller-visible guarantees, and assertions for programming invariants.
- **Explicit guarantees.** Guarantees that code relies on are made explicit unless they are obviously maintained: in the type where the type system can express them, otherwise in a doc comment at the owning boundary and an assertion where they are relied on.
- **Simplifying invariants.** Additional invariants that would simplify code are sought out ("if we can guarantee X, then we could simplify this by Y"); their feasibility, owning layer, and enforcement cost are established, and they are enforced and documented before code relies on them.
- **Invariants, not fallbacks.** Code relies on established invariants and asserts programming violations at their owning boundary. Prefer an invariant or simpler design that removes a condition; an operational alternative required by the contract has a reachable trigger, a defined outcome, and an oracle that exercises it. Yuan et al. found incorrect handling of non-fatal errors in 92% of the 48 catastrophic failures in their study ([source](https://github.com/ReubenBond/research-papers/blob/main/Simple_Testing_Can_Prevent_Most_Critical_Failures/Simple_Testing_Can_Prevent_Most_Critical_Failures.md)).
- **Fix contracts at their owner.** A guarantee stated in a layer's contract is established for its dependents; a layer found violating it has a defect, fixed in that layer with a contract test that would have caught it. Dependents keep relying on the stated contract while the fix lands; compensating checks, retries, fallbacks, or test workarounds added to a dependent are defects. A guarantee the contract lacks is added through a contract change at the owning boundary ([worked example](applied-principles.md#fix-a-broken-guarantee-at-its-owner)).
- **Designed hints.** Caches and directory, routing, and placement entries are specified as possibly stale, define how staleness is detected (validity check, version, or rejection by the authority), and recover through the authoritative path.
- **Illegal states unrepresentable.** External input is converted to validated types at the owning boundary and trusted inside, and revalidated when it crosses another trust boundary ([parse, don't validate](https://github.com/ReubenBond/research-papers/blob/main/Parse_Dont_Validate/Parse_Dont_Validate.md)).
- **Two kinds of error.** Expected failures (remote I/O, timeouts, node failure, storage conflicts, invalid external input, cancellation) are handled explicitly, and a failed local storage operation stops the process (fail-stop, below); product programming errors are caught by side-effect-free `Debug.Assert`. Handlers that are empty or only log, catch overly general exceptions, or are left as `TODO` are defects; these three patterns caused 35% of the catastrophic failures Yuan et al. studied.
- **Assertion policy.** Side-effect-free `Debug.Assert` checks caller preconditions and internal invariants for product programming errors; assertion-enabled builds run in CI and surface assertion failures as test failures. External-input and public-API validation always runs, independent of assertions. Within established contracts, code relies on proven guarantees rather than redundant assertions or checks.
- **Precise assertions.** Each assertion states one precondition, postcondition, or invariant, so a failure identifies the broken term, and covers both what must hold and what must not (for example, an entry is present and not yet disposed).
- **Paired assertions.** An invariant on data crossing a boundary is asserted on both sides: before it is written or sent, and after it is read or received ([pair assertions](https://github.com/ReubenBond/research-papers/blob/main/It_Takes_Two_to_Contract/It_Takes_Two_to_Contract.md)).
- **Safety, then liveness.** Safety holds for every execution admitted by the fault model; progress follows stated quorum, scheduling, and communication assumptions, with deadlines or stall detection where the contract requires them.
- **Failure semantics.** Each interface that can time out, be cancelled, partially complete, see duplicates, or return stale data defines that behavior; a timed-out remote call may still have executed.
- **Durable answers.** A crash never revokes an answer. Whatever an answer asserts (an acknowledgment, a refusal such as sealed or fenced, a read, a tail, a listing, a version, or a value published for other components to read) is durable before the answer leaves its component, so it holds in every state recovery can reach. An answer that reflects a change (its effect, or a refusal it causes) waits for the change's durable outcome, or is an outcome that asserts nothing about state (unavailable, ambiguous, throttled, cancelled). Concurrent operations need no serialization: an operation with no happens-before relation to an in-flight change answers from the durable state before it, as a read concurrent with a create answers that the item is absent. A derived answer (a quorum, a fold, a cache, a forwarded reply) is durable only when every answer it counts is; a hint asserts nothing durable, and no safety decision counts it ([worked example](applied-principles.md#make-answers-durable)).
- **Fail-stop on local storage failure.** A failed local storage operation (a write, flush, fsync, rename, directory flush, or read error from the local disk) stops the process. The component reports it to the process's fatal-error handler (a static handler, or an injected one such as Orleans' `IFatalErrorHandler`) and never ends the process itself; the handler writes a message naming the operation, the path, and the operating-system error, and exits with a distinct exit code, leaving restart or replacement to its orchestrator. The one exception is a recovery which is trivially simple and safe: it answers nothing from the failed state and leaves only a state the crash path already handles, such as removing a temporary file a failed rename left behind. Retrying the failed operation, a degraded mode, or a terminal state which keeps the process alive is never such a recovery: after such a failure the state of the file and of the operating system's caches is unknown (Linux can report an fsync error once and mark the failed pages clean), so only a fresh process recovering from what the device holds knows what is durable. An answer the storage gives (a missing file, an existing name) is not a failure, and a checksum mismatch in bytes read successfully is corruption, handled by the layer's corruption rules ([worked example](applied-principles.md#stop-the-process-on-a-local-storage-failure)).
- **Idempotence.** Retried operations define duplicate behavior end to end, using natural idempotence, stable operation IDs, ETags or versions, or deduplication.
- **Single-owner concurrency.** Single-owner state (actor turns), sharding, and commutative (order-independent) updates are preferred to locks; leases and epochs, rather than distributed locks, govern ownership that moves between nodes.
- **Fencing.** The protected resource checks ownership generation as part of applying a mutation, so work from a superseded owner cannot commit after the cutover ([Chubby](https://github.com/ReubenBond/research-papers/blob/main/The_Chubby_Lock_Service_for_Loosely-Coupled_Distributed_Systems/The_Chubby_Lock_Service_for_Loosely-Coupled_Distributed_Systems.md)).
- **Virtual synchrony.** Each operation takes effect within the configuration that accepted it or not at all: the reconfiguration decision fixes the old configuration's closing state (for example, partition ownership handoff on a membership change), so in-flight work from a sealed configuration never becomes visible later ([Birman, Malkhi, and van Renesse](https://github.com/ReubenBond/research-papers/blob/main/Virtually_Synchronous_Methodology_for_Dynamic_Service_Replication/Virtually_Synchronous_Methodology_for_Dynamic_Service_Replication.md)).
- **Recovery eligibility.** A recovering participant resumes each role after restoring the durable evidence or completing the rebuild protocol that establishes that role's safety guarantees ([Paxos Made Live](https://github.com/ReubenBond/research-papers/blob/main/Paxos_Made_Live_An_Engineering_Perspective/Paxos_Made_Live_An_Engineering_Perspective.md)).
- **Interleaving.** In reentrant or interleaved paths, assumptions about mutable state are re-checked after each `await` at which other work can run.
- **Scheduler ownership.** State owned by a single-threaded scheduler is accessed only on that scheduler: owned code awaits on the captured context, offloaded work (`Task.Run`) returns results without touching owned state, and external callbacks enter through the owner's scheduling entry point.
- **Determinism.** Time (`TimeProvider`), randomness, and external I/O that tests must control are injected so executions reproduce.
- **Async and cancellation.** Operations that accept a `CancellationToken` pass it to every cancellable callee; async code awaits instead of blocking (`.Result`, `.Wait()`, `GetAwaiter().GetResult()`).
- **Ownership and lifetime.** Long-lived resources (timers, subscriptions, connections, `IDisposable`s) have one owner and are released at that owner's boundary: request, entity, component, provider, or process.
- **Security.** The trusted computing base stays small, components hold least privilege, and data is validated according to its trust level before it influences privileged or persistent state.
- **Observability.** Operationally significant failures are diagnosable from logs, metrics, or traces emitted at the owning boundary with stable context (entity ID, node, operation); repeated product log messages use `[LoggerMessage]`.
